# 对抗审查规则（Adversarial Review）

> "左右互搏"机制 — 在文档创建过程中引入对立视角审查，发现逻辑漏洞和需求偏差。
> 基于原则：**创作者和审查者不应是同一人**。

---

## 一、核心机制

### 角色分配

| 角色 | 视角 | 使用技能 | 职责 |
|------|------|---------|------|
| **左派** Review-Champion | 质疑者 | `/ce-review`, `/ce-brainstorm`, `plan-ceo-review`, `plan-eng-review` | 找漏洞、挑战假设、生成替代方案 |
| **右派** PM/Architect | 辩护者 | `product-requirements`, `writing-plans` | 逐条回应、采纳合理挑战、修订文档 |

### 审查流程

```
1. 文档创建者完成初稿
2. [人工干预] 提示用户运行 /adversarial-review
3. 左派 Agent 生成挑战报告（每轮 ≤5 个挑战点）
4. 右派 Agent（文档创建者）逐条回应
5. [人工干预] 用户确认最终版本
```

---

## 二、审查维度

| 维度 | 审查内容 | 权重 |
|------|---------|------|
| **产品价值** | 需求是否真实？用户是否买单？ROI 是否合理？ | 25% |
| **技术可行性** | 架构是否可行？依赖是否合理？性能是否有保障？ | 25% |
| **用户体验** | 流程是否顺畅？交互是否直观？异常处理是否完善？ | 20% |
| **安全性** | 数据是否安全？认证是否完备？边界条件是否处理？ | 15% |
| **可维护性** | 代码结构是否清晰？文档是否充分？是否便于扩展？ | 15% |

---

## 三、审查目标与触发

| 目标文档 | 命令 | 触发时机 |
|---------|------|---------|
| `docs/requirements/PRD.md` | `/adversarial-review prd` | PM 完成 PRD 初稿后 |
| `docs/design/01_系统架构设计.md` | `/adversarial-review design` | Architect 完成架构设计后 |
| `docs/design/03_API接口设计.md` | `/adversarial-review api` | Architect 完成 API 设计后 |
| `docs/design/04_UI设计规范.md` | `/adversarial-review ui` | UI Designer 完成设计规范后 |

---

## 四、挑战报告格式

每个挑战点按以下格式输出：

```markdown
### Challenge #N: {标题}

**维度**: 产品价值 / 技术可行性 / 用户体验 / 安全性 / 可维护性
**严重程度**: Critical / High / Medium
**原文位置**: {文件}:{行号} 或 {章节}
**问题描述**: {具体问题描述}
**替代方案**: {至少一个替代方案}
**建议**: {具体修改建议}
```

---

## 五、回应格式

右派（文档创建者）按以下格式逐条回应：

```markdown
### Response to Challenge #N

**决定**: Accepted / Partially-Accepted / Rejected
**理由**: {接受或拒绝的理由}
**修改内容**: {具体修改了什么，或为什么不修改}
```

---

## 六、限制规则

1. **每轮最多 5 个挑战点** — 避免上下文爆炸
2. **左派不可重复同一论点** — 每个挑战必须是独立的
3. **右派必须逐条回应** — 不可跳过任何挑战
4. **Critical 挑战必须处理** — 不可标记为 Rejected
5. **最多 3 轮** — 如果 3 轮后仍有未解决的关键问题，需要人工介入

---

## 七、人工干预点

| 时机 | 提示模板 |
|------|---------|
| 文档初稿完成 | "{文档名} 初稿已就绪。建议运行 `/adversarial-review {类型}` 进行对抗审查。" |
| 左派完成挑战 | "左派提出了 N 个挑战（Critical: X, High: Y）。请审阅后决定是否修订。" |
| 右派完成回应 | "右派回应了 N 个挑战：Accepted M, Partially-Accepted K, Rejected L。请确认最终版本。" |

---

## 八、与 CE 插件的关系

对抗审查的"左派"角色默认使用 CE 插件的技能：
- `/ce-review` — 多维度专项审查（生成正式评审报告）
- `/ce-brainstorm` — 生成替代方案（至少 2 种实现路径）

如果 CE 插件未安装，左派角色仍可使用内置的 `plan-ceo-review` 和 `plan-eng-review` 进行基础审查。
